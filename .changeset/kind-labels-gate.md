`pick` gains an optional `labels` gate that limits which reference parts reach the decide step. With `labels: { directory, deciderId }` the pick asks the seven kind questions in `LABEL_KINDS` of every reference part and once of the task, through the decide port and batched as decision batches are. A part's label set is stored once in one JSON file per item under `directory`, written to a temporary file and renamed into place, keyed by the question-set version, the caller's `deciderId` and the part's text; the task's set is stored the same way under the task's own key. A later pick over unchanged parts or the same task text asks nothing for them, and a changed part is labelled again. A refused, missing or errored answer is never stored, and a missing, corrupt or wrong-shaped file is a miss.

The label lane holds the parts at probability 0.5 or more on a kind the question itself needs at 0.5 or more, ordered by that probability, and merges with the keyword lanes by rank through reciprocal-rank fusion; the gate is the union of the two. `record.labels` reports the question-set version, the deciderId, how many items' labels were asked and how many reused, how many candidates the gate let through, and how many label sets the store could not write (`failedWrites`, with one `warning` when above 0; the pick still uses those answers); a reference part the keyword lanes never held, left out on its stored or answered labels, records `unassessed` with reason `'gate'`. Label batches count against `maxBatches` and `maxElapsedMs`, so a stop while labelling leaves the decide step unasked, and the label lane is not capped by `maxCandidates`. The option is off by default: with `labels` unset the output is identical to a pick without it.
